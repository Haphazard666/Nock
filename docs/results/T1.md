## Part B: what the spike does

`cargo run --release --example radio_spike` with no URL:

1. Fetches `https://all.api.radio-browser.info/json/servers` with PowerShell `Invoke-RestMethod` (`User-Agent: Nock/0.13.0 (T1 radio spike)`), picks a random server and tries the next one on error. Then it gets the top MP3 and AAC stations by clickcount, plus the first `hls=1` / `.m3u8` station from the top 2000. Directory fetch: 2.0 to 2.3 s.
2. Plays each with `MediaPlayer` (`MediaSource::CreateFromUri(url_resolved)`), measures for 60 s, then stops (Pause, `SetSource(None)`, `Close`, drop).
3. Sets title = station name and artist = country (see the media session section for what worked).
4. Plays `http://127.0.0.1:9/none.mp3` and waits for `MediaFailed`.

"First sound" is measured from the process's own WASAPI session peak meter (`IAudioMeterInformation`, threshold 0.0005), so it doesn't rely on anyone listening. The meter is only polled (every 20 ms) while waiting for first sound and for silence after stop. The 60 s measurement window does no polling. Flags: `--secs`, `--hold`, `--wait`, `--sta`, `--pump`, `--aumid`, `--display early|opened|item`, or pass a URL to play one station.

Stations used (server `de1.api.radio-browser.info`):

| Kind | Station | URL |
|---|---|---|
| MP3 | Radio Armisa (Italy) | https://onair.armisa.it/listen/armisa/radio.mp3 |
| AAC | Christmas FM Non-stop! (Finland), 128k | https://xmas-node1.zip.wf/live.aac |
| HLS | RTL (France), 64k AAC | https://live.m6radio.quortex.io/.../audio-64000/index.m3u8 |
| AAC (extra tests) | Radio Paradise 320k | http://stream-uk1.radioparadise.com/aac-320 |

## Answers

### Does audio play for each format? Play to first sound

Yes for all three, including HLS through a plain `MediaSource::CreateFromUri` (no `AdaptiveMediaSource` code needed).

| Stream | Main run (MTA, 60 s) | Other runs (STA, short runs) |
|---|---|---|
| MP3 | 1259 ms | 888, 1061, 1108, 1239 ms |
| AAC (xmas) | 736 ms | 632, 893 ms |
| AAC (Radio Paradise) | n/a | 475 to 587 ms (8 runs) |
| HLS | 884 ms | 775, 812, 1040, 1663 ms |

All are well inside the spec's 5 s. `MediaOpened` fires 560 to 1013 ms after `Play()`. Creating the player takes 9 to 41 ms.

Not checked by ear: nobody listened. The meter proves samples reached the audio engine for our process.

### Does stop silence it immediately?

Yes. The meter reads silence 4 to 218 ms after the stop call. Most runs were 4 to 30 ms. When it is ~215 ms, that is how long the calls themselves took (`SetSource(None)` + `Close()` sometimes block for ~210 ms on the calling thread, which would be the UI thread in Nock). After stop, the GSMTC session list is empty again.

### Windows media flyout and Nock's Media card

- **Windows session list (GSMTC): yes.** While playing, `GlobalSystemMediaTransportControlsSessionManager` lists one session, the current one, with app id `radio_spike.exe` (in Nock it would be `nock.exe`) and status Playing. GSMTC is the source behind the flyout and Nock's Media card.
- **Title/artist: only if set at the right time.** Setting them through `SystemMediaTransportControls.DisplayUpdater` *before* the source opens (the obvious order) is **wiped**: GSMTC shows an empty title and artist, with or without an AUMID. Two ways work, both tested in MTA and STA:
  - DisplayUpdater (`SetType(Music)`, `MusicProperties.SetTitle/SetArtist`, `Update()`) **after `MediaOpened`** shows "Radio Paradise / United States".
  - `MediaPlaybackItem::Create(source)`, then `GetDisplayProperties()` → set title/artist → `ApplyDisplayProperties`, then `player.SetSource(item)` also works, with no timing dependency. **Recommended for T3.**
- **Installed Nock 0.13: yes.** While the spike played, the running Nock 0.13 pill/top bar showed "Radio Paradise · United States" with the playing indicator (screenshot taken). Nock's `media.rs` reads `GetCurrentSession()` with no app filter, so the panel's Media card reads the same state. I did not open the panel to look at the card itself.
- **Windows volume flyout: not confirmed visually.** I pressed volume up then down (volume ends where it was). The capture showed only the volume slider, and the flyout faded within about a second. Shell windows may be masked in my screenshots. **Yuval: please press a volume key while the spike plays and see if the media tile shows the station.**
- **Nothing extra needed for an unpackaged exe.** No `SetCurrentProcessExplicitAppUserModelID`, no manifest, no package identity. With `--aumid` the session id becomes `Nock.RadioSpike`; otherwise it is the exe name. Nock's Media card would show the friendly name of `nock.exe`.

### `windows` crate features needed

On top of what `Cargo.toml` already enables: **`Media`** (SMTC, `MediaPlaybackType`), **`Media_Core`** (`MediaSource`), **`Media_Playback`** (`MediaPlayer`, `MediaPlaybackItem`, session/state/failed args). `Foundation` (`Uri`, `TypedEventHandler`) is already there via the `media` feature.

The spike's dev-dependency also lists `Media_Control`, `Win32_Media_Audio(_Endpoints)`, `Win32_System_ProcessStatus`, `Win32_System_Diagnostics_ToolHelp`, `Win32_UI_Shell` and `Win32_UI_WindowsAndMessaging`. Those are only for measuring (GSMTC listing, peak meter, memory, thread count, AUMID test, pump). The real `tuner.rs` needs just the three above, and the `media` feature already pulls in `Media_Control`.

### Events, message pump, apartments

| Main thread | `MediaOpened` | `PlaybackStateChanged` | `MediaFailed` | Handler thread |
|---|---|---|---|---|
| MTA, no pump | on time | on time | on time | worker threads |
| STA, **no** pump | **held back ~1.5 s**, until the STA thread next blocks in a COM call | on time | on time (16.3 s, as in MTA) | worker threads |
| STA **with** pump (like Nock's UI thread) | on time | on time | on time | worker threads, never the STA thread |

What this means for Nock: creating the player on the STA UI thread is fine, because Nock's UI thread pumps messages. Handlers **always run on WinRT worker threads**, never the UI thread. So the spec's plan is right and required: the handler only does `PostMessageW(hwnd, WM_APP + n, ...)`, and all state changes happen on the UI thread. No new thread is needed for playback (`MediaPlayer` runs its own Media Foundation pipeline). Don't make blocking WinRT calls (`.join()`) on the UI thread while a source opens.

### CPU and memory (spike process, measured inside the process)

CPU = process kernel+user time over the window. "Machine" = divided by 16 logical CPUs (Task Manager style). "Core" = % of one core. WS = working set (sampled every 1 s). Private = private commit.

| State | CPU machine | CPU one core | WS avg | WS max | Private | Threads |
|---|---|---|---|---|---|---|
| Baseline, before any player | n/a | n/a | 7.3 MB | | 1.3 MB | 4 |
| MP3 playing, 60 s | 0.081 % | 1.30 % | 47.9 MB | 48.4 MB | 12.4 MB | 32 |
| AAC playing, 60 s | 0.070 % | 1.11 % | 52.3 MB | 53.0 MB | 16.3 MB | 34 |
| HLS playing, 60 s | 0.066 % | 1.06 % | 53.8 MB | 54.3 MB | 14.3 MB | 36 |
| AAC 320k playing, 90 s | 0.069 % | 1.10 % | 47.2 MB | 48.6 MB | 14.8 MB | 30 |
| Stopped, 30 s after last stop | **0.000 %** | 0.000 % | 51.2 MB | | 10.0 MB | 21 |
| Stopped, 120 s after stop (separate run) | **0.000 %** | 0.000 % | 42.8 MB | | 7.9 MB | 30 |

STA runs (20 s each) gave the same picture: 0.06 to 0.09 % machine, 47 to 54 MB WS.

CPU is well under the 2 % target either way. The working set grows ~40 to 47 MB over a bare process while playing, mostly from loading the Media Foundation and WinRT DLLs. Private memory grows only 11 to 15 MB. Nock already has WinRT, D2D and DirectWrite loaded, so the extra in Nock will probably be smaller, but **T3 must measure it in Nock**.

## What this proves wrong or missing in the spec

1. **"Set its display title"**: the order matters. A DisplayUpdater title set before the source opens is silently wiped. Use `MediaPlaybackItem` display properties (or DisplayUpdater after `MediaOpened`). Worth a line in the spec.
2. **Criterion 4 / "React to MediaFailed"**: `MediaFailed` alone is not enough.
   - Unresolvable host: fails in 112 ms. HTTP 404: 978 ms.
   - Connection refused (`127.0.0.1:9`): fails after **16.3 s** every time.
   - Blackholed host (`http://example.com:81/x.mp3`, SYN dropped): **no `MediaFailed` and no state change in 120 s.** The UI would show "connecting" forever.

   The real code needs its own connect timeout: a one-shot `SetTimer` started on Play and cancelled on `MediaOpened` (an event, not polling). On expiry, close the player and show the error. 10 s is my suggestion. **PM decision needed**, since the spec says "No polling" and lists only events.
3. **`MediaFailed` gives no message text.** `ErrorMessage` is empty; there is only `MediaPlayerError(4)` (SourceNotSupported) plus an HRESULT (`0xC00D0035`, `0xC00D001A`). The error line text has to come from Nock.
4. **Criterion 6 ("no player exists" when stopped)** holds, and CPU is exactly 0. But the process does **not** go back to its pre-play size: +17 to 26 threads (WinRT/MF thread pool) and ~35 to 45 MB working set stay after stop, still there at 120 s. If T3 checks "no extra threads" by thread count, it will fail. The check should be "no player object, no thread of ours, 0 % CPU".
5. **Criterion 7 (under 40 MB extra)** is borderline on working set in a bare process (+40 to 47 MB). Private memory (+11 to 15 MB) is comfortably under. Suggest saying which counter the target means.
6. **Playback state is noisy.** Radio Armisa flipped Buffering↔Playing 10 times in 12 s while audio kept going. The AAC stream produced sound while the state still said Paused (first sound at 736 ms, `Playing` event shortly after or 1.5 s later). The now-playing strip should not flash errors on `Buffering`, and should not hide "playing" until `Playing`.
7. **HLS is not a codec in Radio Browser.** The top "AAC" list already contained an `.m3u8` (RTL). Station rows have an `hls` 0/1 field. MediaPlayer handles both, so no special path is needed, but codec labels in the list can say "AAC" for HLS streams.
8. Some stations report `bitrate=0` (Radio Armisa). The row needs a "?" or blank.

## Untested

- Hearing the audio by ear (meter-verified only).
- The Windows volume/media flyout tile, visually (see above). Nock's panel Media card itself (the pill showed the title).
